## 使用约定

- 状态：`未开始`、`进行中`、`已完成`、`暂缓`、`已忽略`。
- 优先级：`P1` 表示进入服务化或引入真实外部组件前应处理；`P2` 表示下一轮相关模块改造时处理；`P3` 表示可随功能自然演进。
- 同目录的 [索引与文档 API 待办](索引与文档API待办.md) 专门记录未来文档导入与索引 API 契约，本清单不重复其中的接口设计工作。

## P1：索引与服务化前的基础边界

### 1. 统一向量 Repository 的配置语义

- 状态：`已完成`
- 涉及：`core/settings.py`、`factory/indexing/factory.py`、`repositories/`
- 原问题：`vector_repository.type="memory"` 曾构建本地 JSON Repository，并允许 `memory + persist=true` 的矛盾组合。
- 实施结果：
  - 移除了 `memory` Repository 类型和 `persist` 开关；向量索引产物始终通过 Repository 持久化。
  - 明确 `InMemoryVectorCollection` 是唯一的运行时内存向量容器，Repository 只承担外部持久化。
  - 新增 `app.repositories.registries` 软件包，提供 Vector、Document、Chunk 与 Manifest 四类 Repository Registry；由 `ApplicationFactory` 统一注入 `IndexingFactory`。
- 验收结果：Settings 会拒绝 `memory`；Factory 不再直接构造任何索引持久化 Repository；索引构建和加载均只面向 `local_json` 持久化产物。

### 2. 加强持久化索引的跨产物完整性校验

- 状态：`已完成`
- 涉及：`indexing/pipeline/loader.py`、`indexing/manifests/`、`repositories/`
- 实施结果：
  - 新增 `indexing/integrity.py`，集中校验 Manifest、RawDocument、ParsedDocument、Chunk 与 VectorRecord 的数量、版本和来源身份链。
  - `IndexBuilder` 在写入 `ready` Manifest 前执行完整性校验，并记录 `artifact_integrity` Trace 阶段；失败时维持或写入 `failed` Manifest。
  - `IndexLoader` 先加载全部 Collection，再执行相同校验后构造 `RagIndex`。
  - 基础校验覆盖孤立向量、孤立 Chunk、文档版本漂移、重复 ID、向量 metadata 漂移、数量和维度不一致。
- 后续边界：全文哈希重算、文本片段重建与原子目录替换属于高成本诊断和发布机制，保留到后续持久化治理任务处理。
- 验收结果：缺失、重复、孤立或版本不一致的持久化数据会在构建发布前或加载阶段得到明确错误；新增篡改产物测试覆盖主要关联损坏场景。

### 3. 强化证据变换的来源真实性约束

- 状态：`已忽略`
- 涉及：`retrieval/context/evidence_transformers/`
- 问题：当前校验能保证来源身份、覆盖范围和排序，却不能证明候选文本确实来自声明的 Chunk 片段。
- 实施目标：
  - 为来源保留可验证的文本哈希或原文偏移区间。
  - 校验证据内容可以由来源 Chunk 的指定片段重建。
  - 将“原文摘录”和“模型派生摘要”明确区分，避免派生内容伪装为原文证据。
- 忽略原因：当前学习阶段优先完成主流程和工程边界，不继续投入证据变换的强化校验、安全治理与实现细节。

### 4. 在服务化前引入应用生命周期容器

- 状态：`已完成`
- 涉及：`factory/application.py`、未来 API 应用入口
- 实施结果：
  - 新增 `app/runtime` 软件包：`ApplicationRuntime` 管理在线索引、SearchService、CompareSearchService 与 RAG Pipeline 的启动、复用和释放。
  - `ApplicationFactory.build_runtime()` 只负责组装 Application Runtime，仍不承担运行状态管理。
  - `ApplicationRuntime.lifespan()` 统一管理自身启动和关闭；不依赖 FastAPI 的 `create_web_lifespan()` 直接适配该生命周期，Web Handler 继续只接收已注入的 Service。
- 验收结果：同一 Runtime 生命周期内在线对象会被复用；停止后对象不可再访问；启动失败会清理已创建对象并标记失败状态；Application Runtime 与 Web lifespan 适配器均有独立测试。

### 5. 为未来文档导入 API 限制文件系统访问范围

- 状态：`已完成`
- 涉及：`core/settings.py`、`ingest/loading/access.py`、`factory/configs.py`、`factory/ingestion.py`、未来文档导入应用服务
- 实施结果：
  - 在 `settings.toml` 的 `[ingestion.access]` 中定义 `allowed_source_dirs`；`DocumentSourceAccessSettings` 拒绝空白目录配置。
  - 新增 `DocumentSourceAccessService`：严格解析请求路径与符号链接，要求其存在、为目录、可读取，且位于任一规范化白名单根目录之下。
  - Factory 将 Settings 转换为 `DocumentSourceAccessConfig` 并组装访问服务；`LocalDocumentLoader` 继续只负责加载已经授权的目录，不承担入口访问控制。
  - API 契约仍只做纯数据校验。未来 Documents Handler 必须先调用该服务，再将返回的规范化目录交给索引构建应用服务。
- 验收结果：测试覆盖合法子目录、白名单外路径、`..` 路径穿越、文件、不存在目录、不可读取目录和 Factory 配置接线。

## P2：模型、配置与组合根的持续收敛

### 6. 将 Manifest 的运行兼容性与构建溯源信息分离

- 状态：`已完成`
- 涉及：`indexing/manifests/`、`indexing/pipeline/`、`factory/retrieval.py`、`retrieval/reporting/`
- 实施结果：
  - Manifest Schema 升级至 V4，新增 `artifact_definition`、`runtime_compatibility`、`build_provenance` 与 `storage_locator` 四个语义区域。
  - `artifact_definition_hash` 取代语义模糊的 `config_hash`，只参与产物身份和 `index_id` 计算；`document_set_hash` 继续描述输入语料版本。
  - batch size、超时、重试、构建时间和应用版本进入 `build_provenance`，不再影响加载兼容性或索引身份。
  - Loader 只比较 embedding provider/model/dimension、Repository 类型、距离度量和向量集合 Schema；collection name 仅作为存储定位信息。
  - V3 Manifest 不做隐式迁移，读取时明确提示重新构建，避免旧 hash 语义被静默篡改。
- 验收结果：测试覆盖构建参数变化后索引身份与加载复用不变，以及 embedding 维度变化仍被可靠拒绝。

### 7. 将领域模型从 `core` 归位到各自业务模块

- 状态：`已完成`
- 涉及：`retrieval/models.py`、`retrieval/context/`、`generation/models.py`、`api/presenters/`、顶层 RAG pipeline
- 实施结果：
  - 删除 `core/models.py`，将 `RetrievalSignal`、`RerankSignal` 与 `RetrievedChunk` 迁入 `retrieval/models.py`。
  - 将 `Citation` 与 `RagAnswer` 迁入 `generation/models.py`；生成层显式依赖检索结果模型，而不是反向让检索层依赖生成。
  - ContextPacker 改为输出检索领域的 `ContextCitation`，AnswerGenerator 在生成最终 `RagAnswer` 时将其转换为 `Citation`，消除了 retrieval -> generation 的反向领域依赖。
  - 审查后保留 `core/errors.py`、`core/tracing.py`、`core/metadata.py` 与 `core/settings.py`：前三者是跨领域基础设施；Settings 的按领域拆分已有 P2.9 专项任务，本轮不提前改变其配置加载边界。
- 验收结果：业务模块不再导入 `app.core.models`，`core` 不再拥有特定检索或生成模型；检索来源到最终回答引用的转换有独立测试。

### 8. 完善上下文预算组合校验

- 状态：`暂缓`
- 涉及：`core/settings.py`、`retrieval/context/`
- 问题：当前只约束 `max_context_tokens <= model_context_window`，未校验上下文、提示词预留、输出预留和安全余量之和。
- 延后原因：该校验需要结合子模块 7 的真实 generation 模型窗口、Prompt 模板和输出策略共同确定，避免当前仅按 retrieval 层的静态参数做出不完整约束。
- 实施目标：
  - 校验所有 token 预算之和不超过模型上下文窗口。
  - 在错误信息中指出超出的具体预算项。
- 验收：会导致潜在超窗的配置无法通过启动校验。

### 9. 按领域拆分 Settings 与配置适配器

- 状态：`已完成`
- 涉及：`core/settings/`、`factory/configs/`、各领域 Factory
- 问题：随着 ingest、indexing 与 retrieval 增长，单文件 Settings 和 ConfigFactory 会继续膨胀。
- 实施目标：
  - 按领域拆分 Settings 定义与 Settings 到 Config 的转换逻辑。
  - 保留轻量的聚合入口，避免调用方感知内部文件组织。
  - 继续遵守 `Settings` 表示外部配置、`Config` 表示运行时功能配置的命名约束。
  - 将 `ConfigFactory` 收敛为不可变 Config 快照缓存：同一 `ApplicationFactory` 生命周期内，相同配置只转换一次并复用同一对象。
  - 单次对象组装应向下传递已经取得的 Config，避免同一构建流程内重复调用 ConfigFactory。
  - 不使用模块级或全局单例缓存；如需热更新，重建 Settings、ConfigFactory 与受影响 Runtime，而不是原地修改 Settings 或清空缓存。
- 验收：配置分层仍可被统一加载；每个领域的配置和适配逻辑可以独立阅读与演进；同一应用生命周期内的 Config 身份稳定且不会跨应用实例共享。
- 实施结果：
  - 将原有单文件 `app/core/settings.py` 重构为 `app/core/settings/` 软件包；`environment.py`、`ingestion.py`、`indexing.py`、`retrieval.py` 与 `project.py` 分别维护对应 Settings，包根继续提供原有稳定导入路径。
  - 将原有单文件 `app/factory/configs.py` 重构为 `app/factory/configs/` 软件包；每个领域由不可变的 `XxxConfigAdapter` 一次完成 Settings 到 Config 的转换，`ConfigFactory` 只作为应用级 Config 快照聚合入口。
  - `ConfigFactory` 不使用全局缓存；单个 `ApplicationFactory` 创建其独立快照，所有 `build_*_config()` 方法只返回已创建的同一 Config 实例。
  - Ingestion、Indexing、Retrieval 与 Pipeline Factory 的主要组装流程先读取所属领域快照，再将 Config 显式传递给下级构建步骤。
  - 新增配置快照生命周期测试，覆盖同一 Factory 的身份稳定、复合 Config 的内部引用一致，以及不同 Factory 间不共享对象。
- 验收结果：外部调用仍可通过 `app.core.settings` 与 `app.factory.configs` 的稳定入口访问；领域定义和适配逻辑可独立维护；Config 的复用范围严格限定为单个应用组合根。

### 10. 在下一轮 Retrieval 扩展时拆分 RetrievalFactory

- 状态：`暂缓`
- 涉及：`factory/retrieval.py`
- 问题：Retriever、Reranker、Context 和 Service 的组装集中在一个 Factory 中，后续外部组件接入时会继续增大。
- 实施目标：在真正新增检索组件时，按匹配、后处理、服务等职责拆分内部构建器，同时维持单一公开入口。
- 验收：调用方仍通过稳定的 Retrieval Factory 组装对象；内部实现不再形成巨型构建函数。

### 11. 收紧包级导出边界

- 状态：`未开始`
- 涉及：各模块的 `__init__.py`
- 问题：部分包级初始化会广泛 re-export 实现细节，增加导入链、可选依赖和循环导入风险。
- 实施目标：
  - 只在稳定公共边界导出少量 Protocol、Config 或 Service。
  - 内部软件包避免为方便导入而聚合全部实现。
- 验收：导入任一业务模块不会无必要地初始化无关实现；公共导入路径清晰稳定。
