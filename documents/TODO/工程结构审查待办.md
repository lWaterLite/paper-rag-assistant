## P1：索引与服务化前的基础边界

### 1. 统一向量 Repository 的配置语义

- 状态：`已完成`
- 涉及：`core/settings.py`、`factory/indexing/factory.py`、`repositories/`
- 原问题：`vector_repository.type="memory"` 曾构建本地 JSON Repository，并允许 `memory + persist=true` 的矛盾组合。
- 实施结果：
  - 移除了 `memory` Repository 类型和 `persist` 开关；向量索引产物始终通过 Repository 持久化。
  - 明确 `InMemoryVectorCollection` 是唯一的运行时内存向量容器，Repository 只承担外部持久化。
  - 新增 `app.repositories.registries` 软件包，提供 Vector、Document、Chunk 与 Manifest 四类 Repository Registry；由 `ApplicationFactory` 统一注入 `IndexingFactory`。
- 验收结果：Settings 会拒绝 `memory`；Factory 不再直接构造任何索引持久化 Repository；索引构建和加载均只面向 `local_json` 持久化产物。

### 2. 加强持久化索引的跨产物完整性校验

- 状态：`未开始`
- 涉及：`indexing/pipeline/loader.py`、`indexing/manifests/`、`repositories/`
- 问题：当前加载流程只校验向量数量和维度，未验证文档、Chunk、向量和 Manifest 之间的完整关联。
- 实施目标：
  - 加载文档、Chunk、向量和 Manifest 后再构造运行时索引。
  - 校验文档数、Chunk 数、向量数、维度和各实体引用关系。
  - 校验向量的 `chunk_id`、Chunk 的文档/版本信息与 Manifest 的一致性。
  - 规划后续的原子构建与发布策略，避免半成品索引被加载。
- 验收：缺失、重复、孤立或版本不一致的持久化数据均会在加载阶段得到明确错误。

### 3. 强化证据变换的来源真实性约束

- 状态：`未开始`
- 涉及：`retrieval/context/evidence_transformers/`
- 问题：当前校验能保证来源身份、覆盖范围和排序，却不能证明候选文本确实来自声明的 Chunk 片段。
- 实施目标：
  - 为来源保留可验证的文本哈希或原文偏移区间。
  - 校验证据内容可以由来源 Chunk 的指定片段重建。
  - 将“原文摘录”和“模型派生摘要”明确区分，避免派生内容伪装为原文证据。
- 验收：篡改文本但保留原来源标识的 Transformer 会被拒绝；合法摘录仍可通过校验并保持引用可追溯。

### 4. 在服务化前引入应用生命周期容器

- 状态：`未开始`
- 涉及：`factory/application.py`、未来 API 应用入口
- 问题：`ApplicationFactory` 能正确组装对象，但尚未定义“应用启动时创建、请求期间复用、关闭时释放”的运行时对象边界。
- 实施目标：
  - 保持 `ApplicationFactory` 只承担组合根职责。
  - 引入运行时容器，统一持有已加载的 `RagIndex`、检索服务和问答 Pipeline。
  - 由 Web 框架的 lifespan 创建和关闭容器，Handler 只接受已注入的应用服务。
- 验收：请求处理路径中不再构建索引或加载持久化数据；同一应用生命周期内共享预期的运行时对象。

### 5. 为未来文档导入 API 限制文件系统访问范围

- 状态：`未开始`
- 涉及：`api/contracts/documents.py`、未来文档导入应用服务、Settings
- 问题：当前 API 契约只校验 `source_dir` 非空；真实路由开放后可能允许访问任意本机目录。
- 实施目标：
  - 在应用服务层解析、规范化请求路径。
  - 限制路径必须位于配置的文档根目录白名单内。
  - 拒绝路径穿越、不可读目录和不受支持的来源。
- 验收：请求不能访问白名单外路径；合法目录仍能按既定 ingest 流程工作。

## P2：模型、配置与组合根的持续收敛

### 6. 将 Manifest 的运行兼容性与构建溯源信息分离

- 状态：`未开始`
- 涉及：`indexing/manifests/compatibility.py`、`indexing/manifests/models.py`
- 问题：`embedding_batch_size` 等构建参数被视为加载索引的硬兼容条件，导致无语义影响的配置变更也无法复用索引。
- 实施目标：
  - 将模型、维度、距离度量、集合 Schema 等保留为运行兼容字段。
  - 将批大小、构建时间、工具版本等归为构建溯源字段。
  - 只用运行兼容字段决定索引是否可加载。
- 验收：仅改变批大小不会阻止索引加载；改变 embedding 模型或维度仍会被可靠拒绝。

### 7. 将领域模型从 `core` 归位到各自业务模块

- 状态：`未开始`
- 涉及：`core/models.py`、`retrieval/`、`generation/`
- 问题：检索结果、引用与回答模型仍共存于 `core`，会使基础设施层逐渐成为业务模型汇聚地。
- 实施目标：
  - 将检索信号与 `RetrievedChunk` 迁入 `retrieval/models.py`。
  - 将 `Citation` 与 `RagAnswer` 迁入 `generation/models.py`。
  - 让 `core` 收敛为错误、设置、追踪与通用元数据等跨领域能力。
- 验收：依赖方向保持从业务模块指向 `core`；`core` 不再拥有特定检索或生成业务模型。

### 8. 完善上下文预算组合校验

- 状态：`未开始`
- 涉及：`core/settings.py`、`retrieval/context/`
- 问题：当前只约束 `max_context_tokens <= model_context_window`，未校验上下文、提示词预留、输出预留和安全余量之和。
- 实施目标：
  - 校验所有 token 预算之和不超过模型上下文窗口。
  - 在错误信息中指出超出的具体预算项。
- 验收：会导致潜在超窗的配置无法通过启动校验。

### 9. 按领域拆分 Settings 与配置适配器

- 状态：`未开始`
- 涉及：`core/settings.py`、`factory/configs.py`
- 问题：随着 ingest、indexing 与 retrieval 增长，单文件 Settings 和 ConfigFactory 会继续膨胀。
- 实施目标：
  - 按领域拆分 Settings 定义与 Settings 到 Config 的转换逻辑。
  - 保留轻量的聚合入口，避免调用方感知内部文件组织。
  - 继续遵守 `Settings` 表示外部配置、`Config` 表示运行时功能配置的命名约束。
- 验收：配置分层仍可被统一加载；每个领域的配置和适配逻辑可以独立阅读与演进。

### 10. 在下一轮 Retrieval 扩展时拆分 RetrievalFactory

- 状态：`暂缓`
- 涉及：`factory/retrieval.py`
- 问题：Retriever、Reranker、Context 和 Service 的组装集中在一个 Factory 中，后续外部组件接入时会继续增大。
- 实施目标：在真正新增检索组件时，按匹配、后处理、服务等职责拆分内部构建器，同时维持单一公开入口。
- 验收：调用方仍通过稳定的 Retrieval Factory 组装对象；内部实现不再形成巨型构建函数。

### 11. 收紧包级导出边界

- 状态：`未开始`
- 涉及：各模块的 `__init__.py`
- 问题：部分包级初始化会广泛 re-export 实现细节，增加导入链、可选依赖和循环导入风险。
- 实施目标：
  - 只在稳定公共边界导出少量 Protocol、Config 或 Service。
  - 内部软件包避免为方便导入而聚合全部实现。
- 验收：导入任一业务模块不会无必要地初始化无关实现；公共导入路径清晰稳定。
