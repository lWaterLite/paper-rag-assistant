# 子模块 2：文档加载、解析与清洗概念教学

对应学习路线：模块 2《RAG 知识库与检索增强生成》子模块 2  
核心项目：`paper-rag-assistant`  
学习定位：把子模块 1 中偏 demo 的文本加载能力，升级为接近真实工程的文档 ingestion 子系统

---

## 1. 子模块 2 要解决什么问题

子模块 1 已经搭好了 RAG pipeline 的骨架：

```text
load -> parse -> chunk -> embed -> store -> retrieve -> pack context -> generate
```

但子模块 1 的 `LocalTextLoader` 只支持 Markdown 和 TXT，本质上还是为了讲清数据流。真实 RAG 项目不会只面对干净的纯文本文件，而是会面对：

- arXiv 或论文官网下载的 PDF。
- 你自己写的 Markdown 笔记。
- 论文项目主页、博客、官方文档等 HTML 页面。
- 部分格式混乱、metadata 缺失、编码异常、内容为空或损坏的文件。

所以子模块 2 的核心问题是：

> 如何把不同来源、不同格式、质量参差不齐的真实文档，稳定转换成后续 chunking 和检索可以使用的统一文档结构。

这一步叫 ingestion，也就是文档摄取。它不是简单的“读取字符串”，而是一组工程能力：

- 识别文件类型。
- 读取真实文件。
- 提取正文。
- 保留页码、章节、来源路径、URL、标题等 metadata。
- 清洗明显噪声。
- 记录解析质量问题。
- 对失败文件做错误隔离，而不是让整个索引流程崩掉。

如果 ingestion 做不好，后面的 embedding、向量库、rerank、LLM prompt 再复杂也很难救回来。

## 2. 为什么真实文档解析比读取文本复杂

很多初学 RAG 的项目会从下面这种代码开始：

```python
text = path.read_text(encoding="utf-8")
```

这对 Markdown 和 TXT 有时够用，但对真实论文 PDF 和网页远远不够。

原因是不同格式的“文档结构”完全不同。

### 2.1 Markdown 是接近语义化的文本

Markdown 比较友好，因为它本身就是文本，而且保留了部分结构信息：

- `#`、`##` 表示标题层级。
- `-`、`1.` 表示列表。
- ``` 表示代码块。
- `|` 可能表示表格。
- 链接和图片有固定语法。

Markdown 的解析难点通常不是“能不能读出文字”，而是：

- 是否保留标题层级。
- 是否保留代码块。
- 表格是否转成纯文本、Markdown 表格，还是结构化表格。
- YAML frontmatter 中的 title、authors、tags、date 是否提取到 metadata。

### 2.2 HTML 是结构化但充满噪声的页面

HTML 看起来有 DOM 结构，但真实网页中大量内容不是正文：

- 导航栏。
- 页脚。
- 侧边栏。
- 广告。
- 推荐文章。
- Cookie 提示。
- 评论区。
- 分享按钮。
- 隐藏脚本和样式。

因此 HTML 解析不是简单地对整个页面调用 `get_text()`。真实工程中通常要做两件事：

1. 找到 main content。
2. 丢弃 boilerplate noise。

对论文项目主页、博客文章和官方文档来说，HTML 解析质量直接影响检索质量。如果导航栏和页脚反复进入索引，检索时可能会召回大量无意义片段。

### 2.3 PDF 是视觉格式，不是天然语义格式

PDF 是最麻烦的。它的设计目标主要是“在屏幕或纸上显示得正确”，不是“让程序理解正文结构”。

一个 PDF 页面里，文本可能只是按照坐标散落在页面上的字块。解析器要猜：

- 哪些字属于同一行。
- 哪些行属于同一段。
- 两栏论文应该先读左栏还是右栏。
- 页眉页脚是否要删除。
- 页码是否是正文。
- 表格应该怎么提取。
- 公式应该保留、忽略，还是转换。
- 图片 caption 是否属于正文。
- 参考文献是否应该进入索引。

pypdf 官方文档也明确指出，PDF 文本提取困难的根源之一是 PDF 缺少可靠的语义层，页眉、页脚、段落、表格和页码等通常只能通过启发式规则推断。PyMuPDF 文档也提到，PDF 提取出的文本可能出现非自然阅读顺序和意外换行，需要利用 block、word、坐标等信息重建顺序。

这就是为什么真实 RAG 项目中，PDF ingestion 往往是第一批需要认真打磨的模块。

## 3. Loading、Parsing、Cleaning 的区别

这三个词很容易混在一起，但在工程中最好分开。

### 3.1 Loading：把外部资源读进系统

Loading 负责从某个来源读取原始内容。

输入可能是：

- 本地文件路径。
- 本地目录。
- URL。
- 对象存储地址。
- 数据库记录。

输出应该保留最原始的信息，例如：

- `source_path`
- `url`
- `file_type`
- `raw_bytes`
- `raw_text`
- `content_hash`
- `loaded_at`
- `file_size`

Loading 不应该做太多清洗。它的职责是可靠地拿到原始材料，并记录来源。

### 3.2 Parsing：把格式转换成统一结构

Parsing 负责理解文件格式，并把它转换成统一的内部结构。

例如：

- PDF -> 每页文本、页码、页面尺寸、文本块。
- Markdown -> 标题层级、正文、frontmatter。
- HTML -> 标题、正文段落、URL、发布日期、作者。

Parsing 的目标不是让文本最短，而是让信息结构清楚。

在真实工程中，解析结果最好不要只有一个大字符串，而应该至少保留：

- 文档级 metadata。
- 页面或章节级 metadata。
- 文本段落。
- 每段文本来自哪里。
- 解析质量问题。

### 3.3 Cleaning：在不破坏引用能力的前提下减少噪声

Cleaning 负责处理明显影响检索的噪声。

常见清洗包括：

- 合并 PDF 中错误断行。
- 删除重复页眉页脚。
- 规范连续空白。
- 修复被断开的英文连字符。
- 删除 HTML 导航栏和脚本样式。
- 保留章节标题。
- 标记而不是直接删除疑似参考文献、表格、公式。

Cleaning 有一个重要原则：

> 不要为了让文本看起来更干净，而丢掉后续 citation、过滤、评测需要的信息。

例如，页码看起来像噪声，但如果你删除页码和页面边界，后续回答就无法说“这个结论来自第 4 页”。章节标题看起来会重复，但它对检索非常重要。

## 4. 原始文本、规范化文本、结构化段落

子模块 2 需要建立一个重要意识：文档不应该只被看成一个 `str`。

真实系统中可以把文本分成三个层次。

### 4.1 Raw Text

Raw text 是解析器直接提取出来的文本，尽量少改动。

作用：

- 用于调试解析质量。
- 用于重新清洗。
- 用于检查是否过度清洗。
- 用于生成解析报告。

Raw text 可能很乱：

```text
Retrieval-Augmented
Generation improves...

1 Introduction

Page 1
```

但它能告诉你原始解析器到底拿到了什么。

### 4.2 Normalized Text

Normalized text 是经过基础清洗后的文本。

例如：

- 合并段落中错误换行。
- 去掉重复页眉页脚。
- 规范空白。
- 保留标题和章节。

这是后续 chunking 最常用的输入。

### 4.3 Structured Blocks

Structured blocks 是比纯文本更细的结构单元。

一个 block 可以表示：

- 标题。
- 段落。
- 列表项。
- 表格。
- 图片 caption。
- 参考文献条目。
- 代码块。

每个 block 都应该携带 metadata：

```text
block_id
doc_id
page_start
page_end
section
text
block_type
char_start
char_end
source_path
```

后续 chunking 可以基于 block 合并，而不是盲目按字符切分。

## 5. 文档身份与版本

子模块 1 已经实现了 `doc_id`、`content_hash`、`version_id`。子模块 2 要继续沿用这个思想，但面对更多来源。

### 5.1 doc_id

`doc_id` 表示“这份文档是谁”。

对本地文件，可以基于规范化路径生成：

```text
doc_id = hash(resolved_source_path)
```

对 URL，可以基于规范化 URL 生成：

```text
doc_id = hash(canonical_url)
```

对 DOI，可以基于 DOI 生成：

```text
doc_id = hash(doi)
```

真实工程中，最理想的优先级通常是：

```text
doi / canonical_url / resolved_path
```

因为论文文件可能被移动路径，但 DOI 不变。

### 5.2 content_hash

`content_hash` 表示“这次读到的内容是什么”。

如果同一个 PDF 文件被替换，`doc_id` 可以不变，但 `content_hash` 应该变化。

### 5.3 version_id

`version_id` 表示“同一文档的某个内容版本”。

通常可以由：

```text
doc_id + content_hash
```

共同生成。

后续增量索引、embedding cache、过期 chunk 删除，都依赖这个概念。

## 6. Metadata 为什么这么重要

RAG 中的 metadata 不是装饰品，它会影响检索、引用、过滤、评测和可观测性。

### 6.1 检索需要 metadata

例如用户问：

> “只根据 2023 年以后的论文回答。”

如果 metadata 中没有 `year`，系统无法过滤。

再比如：

> “找 RAG evaluation 相关内容，不要返回参考文献部分。”

如果没有 `section` 或 `block_type`，系统无法判断某个 chunk 是否来自 references。

### 6.2 引用需要 metadata

一个可靠 citation 至少需要：

- 文档标题。
- 来源路径或 URL。
- 页码或章节。
- chunk id。
- snippet。

如果 PDF 解析时没有保留页码，后面就只能引用“某个文件”，无法引用“某一页”。

### 6.3 评测需要 metadata

后续做 RAG evaluation 时，我们需要知道：

- 正确答案应该来自哪篇文档。
- 应该来自哪个 section。
- 是否命中了正确页面。
- 检索结果是否来自错误版本。

这些都依赖 metadata。

### 6.4 排查问题需要 metadata

如果用户发现回答错误，我们需要追踪：

```text
用户问题
  -> 检索到了哪些 chunk
  -> chunk 来自哪些文档
  -> 文档是哪个版本
  -> chunk 来自哪个页面/章节
  -> 原始解析文本是否已经错了
```

没有 metadata，就只能猜。

## 7. PDF 解析中的真实问题

下面这些问题会直接导致 RAG 错误。

### 7.1 错误断行

论文 PDF 常常会把一个自然段拆成很多视觉行：

```text
Retrieval-Augmented Generation
improves factual grounding by
conditioning generation on external
documents.
```

如果不修复，embedding 仍然大致可用，但 chunk 的文本质量会下降，生成回答也可能变得不自然。

英文中还会出现断词：

```text
retrieval-
augmented generation
```

应该尽量恢复为：

```text
retrieval-augmented generation
```

或在某些场景恢复为：

```text
retrieval augmented generation
```

具体规则要谨慎，因为有些连字符本来就是术语的一部分。

### 7.2 页眉页脚重复

论文页眉页脚可能每页重复：

```text
Proceedings of ...
Page 3
```

如果这些内容进入索引，会造成两个问题：

- 重复内容污染 embedding。
- 检索时召回无意义 chunk。

工程上可以统计每页顶部和底部重复出现的短文本，把高频重复项标记为 header/footer。

### 7.3 双栏排版

很多论文是双栏。如果解析器按错误顺序读取，可能变成：

```text
左栏第一行
右栏第一行
左栏第二行
右栏第二行
```

这会严重破坏语义。

工程上需要利用坐标信息或解析器的阅读顺序能力。只拿 plain text 往往不够。

### 7.4 表格

表格不是普通段落。直接抽成文本可能丢失行列关系。

例如：

```text
Method Recall MRR
BM25 0.51 0.42
Dense 0.68 0.55
```

如果列对齐丢失，模型可能误解数值属于哪个方法。

子模块 2 阶段不一定要完整结构化表格，但至少要识别“这是表格或疑似表格”，并保留原文，避免悄悄破坏。

### 7.5 公式

公式通常很难从 PDF 中可靠提取。可能出现：

- 完全丢失。
- 顺序错乱。
- 符号变成乱码。
- 上下标丢失。

对论文 RAG 来说，公式可以先作为低优先级处理，但要记录 parse issue。

### 7.6 参考文献

参考文献既可能有用，也可能污染检索。

有用的情况：

- 用户问某篇论文引用了哪些工作。
- 用户想追踪某个方法来源。

污染的情况：

- 用户问论文方法，结果检索召回 references 中的标题。

比较稳妥的做法是：

- 不直接删除 references。
- 标记 `section="References"` 或 `block_type="reference"`。
- 检索时根据场景决定是否过滤。

### 7.7 扫描版 PDF

扫描版 PDF 本质上是图片，普通文本提取工具可能拿不到文字。

这类文档需要 OCR。OCR 不是本子模块第一优先级，但工程上要能识别：

- 该 PDF 是不是几乎没有可提取文本。
- 是否需要进入 OCR fallback。
- OCR 质量是否低。

## 8. Markdown 解析中的真实问题

Markdown 看似简单，但真实工程里也有坑。

### 8.1 Frontmatter

很多 Markdown 文件开头有 YAML frontmatter：

```yaml
---
title: "RAG Evaluation Notes"
authors:
  - Alice
  - Bob
date: 2024-05-10
tags:
  - rag
  - evaluation
---
```

这些内容应该进入 metadata，而不是混在正文里。

### 8.2 代码块

代码块不能随意清洗缩进，否则含义会改变。

例如 Python、JSON、YAML 代码块，后续检索时可能很重要。

### 8.3 表格

Markdown 表格至少应该保留原样，后续再决定是否结构化。

### 8.4 链接与图片

链接文本和 URL 都有价值：

```markdown
[RAG paper](https://example.com/paper)
```

清洗时可以保留成：

```text
RAG paper (https://example.com/paper)
```

图片本身无法直接进入文本检索，但 alt text 和 caption 可能有价值。

## 9. HTML 解析中的真实问题

HTML 文档通常有两种来源：

- 本地保存的 HTML 文件。
- 从 URL 下载的网页。

子模块 2 建议先支持本地 HTML 文件，后续再扩展在线抓取。

### 9.1 DOM 解析

Beautiful Soup 适合遍历 HTML/XML parse tree，提取标题、正文、链接、meta 标签等。

但它不自动知道“正文在哪里”。如果直接：

```python
soup.get_text()
```

很容易把导航、页脚和脚本周边文本也抽进来。

### 9.2 Main Content Extraction

更接近真实工程的做法是：

- 优先识别 `<article>`、`<main>`。
- 其次根据常见 class/id，例如 `content`、`post`、`paper`。
- 对普通网页可以考虑 Trafilatura 这类正文抽取工具。

Trafilatura 的定位就是从网页中提取正文、metadata 和相关结构，适合后续作为 HTML ingestion 的候选方案。

### 9.3 Metadata

HTML 中 metadata 可能来自：

- `<title>`
- `<meta name="author">`
- `<meta name="description">`
- `<meta property="og:title">`
- `<link rel="canonical">`
- 页面中的发布日期。

对网页 RAG 来说，`canonical_url` 很重要，因为同一页面可能有多个 URL 变体。

## 10. 统一 Loader 接口

子模块 2 的工程目标不是写三个互不相干的函数，而是建立统一抽象。

一个合理的方向是：

```text
DocumentLoader
  -> PDFLoader
  -> MarkdownLoader
  -> HTMLLoader
```

统一接口可以类似：

```text
load(source: DocumentSource) -> LoadResult
```

或者：

```text
load_file(path: Path) -> RawDocument
```

但随着真实需求增加，`RawDocument` 可能需要扩展为能表达更多状态：

```text
RawDocument
  doc_id
  source_path
  source_uri
  file_type
  content_hash
  version_id
  raw_bytes
  raw_text
  metadata
```

如果暂时不想把 `raw_bytes` 放进 dataclass，也可以在 loader 内部计算 hash 后只保留必要文本和 metadata。

关键是所有 loader 都要输出统一结构，后续 parser/chunker 不应该关心文档原本是 PDF、Markdown 还是 HTML。

## 11. 统一 Parser 输出

当前项目已有 `ParsedDocument`：

```text
doc_id
content_hash
version_id
title
text
source_path
metadata
```

子模块 2 可以继续使用它，但从真实工程看，建议逐步扩展出更细粒度的结构。

例如：

```text
ParsedDocument
  doc_id
  version_id
  title
  text
  source_path
  metadata
  blocks
  parse_issues
```

其中 `blocks` 可以包含：

```text
ParsedBlock
  block_id
  block_type
  text
  page_start
  page_end
  section
  char_start
  char_end
  metadata
```

这样做有几个好处：

- chunker 可以按 block 合并。
- citation 可以追溯到页码和章节。
- evaluation 可以检查命中的是不是正确 section。
- 清洗策略可以按 block_type 区分。

例如：

- 标题块不要和正文同样处理。
- 代码块不要合并缩进。
- 表格块不要随便折行。
- references 块可以被检索策略过滤。

## 12. 清洗策略的边界

清洗不是越多越好。

### 12.1 应该做的清洗

适合在子模块 2 做的清洗：

- 去除明显重复页眉页脚。
- 合并同一段落中的错误换行。
- 规范连续空白。
- 保留 Markdown 标题层级。
- 提取 frontmatter metadata。
- 移除 HTML script/style/nav/footer。
- 识别空文档和低质量解析。

### 12.2 暂时不应过度做的清洗

这些可以先标记，不要贸然删除：

- 参考文献。
- 表格。
- 公式。
- 图片 caption。
- 脚注。
- 附录。

原因是它们在某些查询场景中是有价值的。

### 12.3 清洗应可解释

每个清洗策略最好能记录：

```text
rule_name
before_length
after_length
affected_pages
issue_count
```

这样后续发现解析质量问题时，可以知道是哪一步造成的。

## 13. 解析失败不应中断整个索引

真实知识库中经常会有坏文件：

- 空文件。
- 损坏 PDF。
- 加密 PDF。
- 非 UTF-8 文本。
- HTML 格式不完整。
- 文件扩展名和实际内容不一致。

如果一个文件失败就让整个索引流程中断，用户体验会很差。

更工程化的做法是：

```text
IngestionResult
  succeeded_documents
  failed_documents
  warnings
  trace
```

失败文件应该记录：

```text
source_path
error_code
error_message
stage
trace_id
```

例如：

```text
document_parse_failed
source_path=data/raw/papers/broken.pdf
reason=PDF 文件损坏，无法读取 xref table
```

这不代表永远不能抛异常。对于配置错误、目录不存在、权限错误等系统性问题，抛出错误是合理的。但对于批量文档中的单个坏文件，应尽量隔离。

## 14. 解析质量如何影响 RAG

下面是三个典型例子。

### 14.1 页眉页脚污染导致检索错误

如果每页都有相同会议名称，向量库里会出现大量重复短语。

用户问某个概念时，检索可能召回含有重复页眉的 chunk，而不是正文。

### 14.2 双栏顺序错误导致语义破坏

如果左栏和右栏交错，chunk 中会混入两段不相关内容。

embedding 会表示一个混乱语义，检索分数变得不可靠，LLM 也可能基于错乱上下文回答。

### 14.3 丢失章节和页码导致 citation 不可信

如果解析时只保留全文字符串，不记录页码和 section，最终回答只能引用文件名。

这会让用户很难核查答案，也无法在评测中判断回答是否命中正确位置。

## 15. 本项目后续建议的真实工程方向

从子模块 2 开始，建议把 ingestion 设计成可扩展模块，而不是简单扩写 `LocalTextLoader`。

建议结构：

```text
app/
  ingest/
    loaders/
      base.py
      pdf.py
      markdown.py
      html.py
    parsers/
      base.py
      pdf.py
      markdown.py
      html.py
    cleaners/
      base.py
      text.py
      pdf.py
      html.py
    quality.py
    pipeline.py
```

如果当前项目不想一次性拆这么细，也至少可以先形成这些边界：

```text
DocumentLoader
DocumentParser
DocumentCleaner
IngestionPipeline
IngestionReport
```

### 15.1 PDF 方案建议

真实工程中可以优先考虑：

- `PyMuPDF`：速度快，能获取文本块、坐标、页码，适合需要 layout 信息的 PDF 解析。
- `pypdf`：轻量，适合基础 PDF 文本和 metadata 读取，也适合教学理解 PDF 提取问题。
- OCR 工具：后续处理扫描版 PDF 时再引入。

如果我们后续要做论文 RAG，建议优先选择 `PyMuPDF` 作为 PDF loader/parser 的基础，因为页面、block、坐标和阅读顺序控制更有用。

### 15.2 Markdown 方案建议

可以先用标准库读取文件，再结合：

- frontmatter 解析。
- Markdown AST 或轻量规则。
- 标题层级提取。

如果后续需要高质量结构化 Markdown，可以考虑 `markdown-it-py`、`mistune` 这类库。

### 15.3 HTML 方案建议

可以分两层：

- 用 `BeautifulSoup` 处理本地 HTML、meta 标签、DOM 清理。
- 用 `trafilatura` 处理通用网页正文抽取。

这样既能学会基础 DOM 操作，也能接近真实网页正文抽取场景。

```text

    rag_*.pdf
  markdown/
    rag_notes.md
    evaluation_notes.md
  html/

```

论文可以选择公开可下载的 AI/RAG 相关论文 PDF。HTML 可以选择论文项目页、官方博客或保存下来的网页。

每份文档都应该在解析报告中记录：

- 文件名。

- 提取文本长度。
- 标题。
- 作者。
- 年份。
- DOI 或 URL，如果有。
- 解析问题。

baseline 数据不要求大，5 篇真实文档比 100 篇 mock 文本更有价值。

## 17. 子模块 2 的验收理解

学习路线中的验收标准可以理解为下面这些能力。

### 17.1 至少支持 PDF 和 Markdown

这意味着项目不能只依赖 `Path.read_text()`。

至少要有：

- PDF 文本提取。
- Markdown 文本和 metadata 提取。
- 不同 loader 的统一接口。

HTML 可以作为增强项，但我们会尽量也支持，因为真实知识库常见网页来源。

### 17.2 每个解析后的文档都有稳定 doc_id

无论输入是 PDF、Markdown 还是 HTML，都应该走统一文档身份策略。

### 17.3 每段文本能追溯来源

这意味着不能只输出一个无来源的大字符串。

至少要保留：

- `doc_id`
- `source_path`
- `page_start/page_end` 或 `section`
- `block_type`

### 17.4 至少 5 个解析器测试

建议测试覆盖：

- 空文件。
- 损坏 PDF 或无法解析文件。
- 中文 Markdown。
- 英文论文 PDF。
- HTML 去噪。
- 缺失 title/author metadata。
- PDF 页码保留。

### 17.5 能列出 PDF 解析失败导致 RAG 错误的例子

至少能解释：

- 双栏顺序错误。
- 页眉页脚污染。
- 页码/章节丢失。
- 表格结构错乱。
- 公式乱码。
