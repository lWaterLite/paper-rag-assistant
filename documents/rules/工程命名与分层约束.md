# paper-rag-assistant 工程命名与分层约束

本文档记录 `paper-rag-assistant` 项目后续开发和重构时需要遵守的命名与分层规则。

它的作用不是限制实现方式，而是让项目里的类名、文件名、配置名和职责边界保持一致，避免随着子模块增加出现概念混淆。

---

## 1. 总体原则

本项目遵守以下原则：

1. 名称必须反映职责，不使用过大的词。
2. 同一类概念在全项目中使用同一套命名规则。
3. 运行时对象、持久化对象、配置对象、流程对象要分层命名。
4. 业务流程依赖抽象接口或运行时对象，不直接依赖文件、数据库或第三方 SDK。
5. 外部配置读取和功能类运行配置必须分离。
6. Factory 是对象组装入口，底层类不自己偷偷构造默认依赖。
7. Writer 只负责写内容，不负责准备目录或决定流程阶段。
8. 测试可以显式注入依赖，但生产入口应通过 factory 统一组装。

## 2. Settings 与 Config

### 2.1 命名规则

```text
Settings
  从外部配置源直接读取出来的配置结构

Config
  转换后传给功能类使用的运行时配置结构
```

示例：

```text
EmbeddingSettings
  对应 settings.toml 中的 [embedding]

EmbeddingConfig
  传给 MockEmbeddingClient / OpenAIEmbeddingClient 使用
```

```text
VectorStoreSettings
  对应 settings.toml 中的 [vector_store]

VectorStoreConfig
  传给 vector 相关运行时对象或 repository 使用
```

### 2.2 Settings 的职责

Settings 负责：

1. 描述外部配置文件或环境变量的字段结构。
2. 做外部配置入口的基本校验。
3. 把字符串、路径、布尔值、数字等转换为 Python 类型。
4. 给用户提供清晰的配置错误。

Settings 不负责：

1. 执行业务逻辑。
2. 创建目录。
3. 创建功能类对象。
4. 调用外部服务。
5. 直接参与 pipeline。

### 2.3 Config 的职责

Config 负责：

1. 作为功能类构造参数。
2. 保护功能模块的输入边界。
3. 提供功能类需要的运行时参数。
4. 封装少量与配置强相关的路径推导。

Config 不负责：

1. 读取 TOML、`.env` 或环境变量。
2. 知道配置来自哪里。
3. 直接写文件或访问数据库。

### 2.4 转换位置

Settings 到 Config 的转换必须发生在 factory 层。

推荐：

```python
def build_embedding_config(project_settings: ProjectSettings) -> EmbeddingConfig:
    return EmbeddingConfig(
        provider=project_settings.embedding.provider,
        model=project_settings.embedding.model,
        dimension=project_settings.embedding.dimension,
    )
```

不推荐：

```python
class MockEmbeddingClient:
    def __init__(self, settings: ProjectSettings) -> None:
        ...
```

原因：

1. 功能类不应该持有整个项目配置。
2. 功能类不应该知道外部配置结构。
3. 后续配置来源变化时，不应该修改功能类。

## 3. Collection 与 Repository

### 3.1 核心约束

本项目采用以下命名规则：

```text
Collection
  运行时内存对象
  管理已经加载或已经处理好的领域数据
  提供查询、添加、更新、遍历、检索等行为
  不直接读写文件或数据库

Repository
  持久化适配器
  负责从文件或数据库加载 Collection
  负责把 Collection 保存到文件或数据库
  不负责业务检索逻辑
```

### 3.2 为什么不用 Store

不优先使用 `Store` 的原因：

1. 在 RAG 和向量数据库语境中，`VectorStore` 经常表示 Chroma、FAISS、Qdrant、pgvector 等外部向量存储后端。
2. 如果本项目把 `Store` 定义成内存运行时对象，容易和外部资料、框架命名冲突。
3. `Store` 的语义偏泛，既可能表示内存容器，也可能表示持久化后端。

因此后续新代码中优先使用：

```text
VectorCollection
ChunkCollection
DocumentCollection
```

而不是：

```text
VectorStore
ChunkStore
DocumentStore
```

### 3.3 为什么不用 Index

不优先使用 `Index` 命名运行时数据容器的原因：

1. 项目中已经存在 `indexing`、`IndexBuilder`、`IndexManifest`、`index_loader` 等概念。
2. `Index` 容易同时表示“索引构建流程”“索引产物”“向量检索结构”，语义过载。
3. 后续做 index version、manifest、loader 时容易混淆。

因此内存运行时对象使用 `Collection`，索引构建流程继续使用 `IndexBuilder`。

### 3.4 Vector 示例

推荐结构：

```text
VectorCollection
  add(record)
  search(query_vector, top_k)
  count()
  contains(chunk_id)
  dimension

VectorRepository
  load() -> VectorCollection
  save(collection: VectorCollection) -> None
```

具体实现：

```text
InMemoryVectorCollection
LocalJsonVectorRepository
```

职责边界：

```text
VectorCollection
  负责内存中的向量管理和相似度搜索
  不知道数据来自 JSON、SQLite、Qdrant 还是 pgvector

VectorRepository
  负责持久化读写
  不做相似度搜索
```

索引构建阶段：

```text
EmbeddingClient
  -> 生成 vector
  -> VectorCollection.add(...)
  -> VectorRepository.save(vector_collection)
```

在线加载阶段：

```text
VectorRepository.load()
  -> VectorCollection
  -> Retriever 使用 VectorCollection.search(...)
```

### 3.5 Chunk 示例

推荐结构：

```text
ChunkCollection
  add(chunk)
  add_many(chunks)
  get_by_id(chunk_id)
  get_by_ids(chunk_ids)
  iter_chunks()
  iter_by_doc_id(doc_id)

ChunkRepository
  load() -> ChunkCollection
  save(collection: ChunkCollection) -> None
```

具体实现：

```text
InMemoryChunkCollection
LocalJsonChunkRepository
```

设计目标：

1. `VectorCollection` 只保存 `chunk_id`、vector 和轻量 metadata。
2. `ChunkCollection` 保存完整 `DocumentChunk`。
3. `Retriever` 先查 vector，再根据 `chunk_id` 查 chunk。
4. 最终统一组装成 `RetrievedChunk`。

### 3.6 Document 示例

推荐结构：

```text
DocumentCollection
  save_raw(raw_document)
  save_parsed(parsed_document)
  get_raw(doc_id)
  get_parsed(doc_id)
  iter_raw()
  iter_parsed()

DocumentRepository
  load() -> DocumentCollection
  save(collection: DocumentCollection) -> None
```

具体实现：

```text
InMemoryDocumentCollection
LocalJsonDocumentRepository
```

### 3.7 命名模板

统一模板：

```text
InMemory{Domain}Collection
LocalJson{Domain}Repository
SQLite{Domain}Repository
Postgres{Domain}Repository
Qdrant{Domain}Repository
```

示例：

```text
InMemoryVectorCollection
LocalJsonVectorRepository

InMemoryChunkCollection
LocalJsonChunkRepository

InMemoryDocumentCollection
LocalJsonDocumentRepository
```

## 4. Client

### 4.1 命名规则

```text
Client
  外部服务或外部模型的调用封装
```

示例：

```text
EmbeddingClient
OpenAIEmbeddingClient
LLMClient
RerankerClient
```

### 4.2 Client 的职责

Client 负责：

1. 调用外部服务、SDK 或模型。
2. 把外部返回格式转换为项目内部格式。
3. 处理 provider 级别的超时、重试、错误转换。
4. 保护 API key，不把敏感信息写入日志或报告。

Client 不负责：

1. 决定业务流程。
2. 保存索引。
3. 持久化业务数据。
4. 读取整个 ProjectSettings。

示例：

```text
IndexBuilder
  依赖 EmbeddingClient 协议

OpenAIEmbeddingClient
  是 EmbeddingClient 的一种实现
```

## 5. Builder

### 5.1 命名规则

```text
Builder
  构建某个复杂产物或执行某条离线构建流程
```

示例：

```text
IndexBuilder
```

### 5.2 Builder 的职责

Builder 负责：

1. 编排多个步骤。
2. 调用多个依赖对象。
3. 生成一个复杂产物。
4. 记录构建过程中的 report、manifest、trace。

Builder 不负责：

1. 自己偷偷创建默认依赖。
2. 直接读取 TOML 或 `.env`。
3. 承担底层持久化细节。
4. 承担在线请求阶段逻辑。

`IndexBuilder` 的职责是离线构建索引，不负责在线问答。

---

## 6. Loader

### 6.1 命名规则

```text
Loader
  从某个输入来源加载原始数据或已有运行时对象
```

当前项目中有两类 Loader：

```text
DocumentLoader
  从文件系统加载原始文档

IndexLoader
  从已有索引产物加载运行时索引对象
```

### 6.2 Loader 与 Repository 的区别

```text
Repository
  偏领域数据持久化
  例如 ChunkRepository、VectorRepository

Loader
  偏流程入口
  可以组合多个 repository、manifest、config 校验
```

例如未来可以有：

```text
IndexLoader
  使用 VectorRepository 加载 VectorCollection
  使用 ChunkRepository 加载 ChunkCollection
  读取 IndexManifest
  校验配置兼容性
  返回 RagIndex
```

## 7. Writer 与 Report

### 7.1 命名规则

```text
Report
  一次流程的结构化结果摘要

Writer
  把结果写入指定目标
```

示例：

```text
IngestionReportWriter
ChunkingReportWriter
IndexBuildReportWriter
```

### 7.2 Writer 的职责

Writer 负责：

1. 把已有结果转换为可序列化结构。
2. 写入调用方提供的路径。
3. 返回写入路径。

Writer 不负责：

1. 创建目录。
2. 决定文件名。
3. 决定何时写。
4. 读取 Settings。
5. 参与 pipeline 决策。

目录创建和流程阶段准备由 Builder 或 Pipeline 负责。

---

## 8. Manifest

### 8.1 命名规则

```text
Manifest
  描述某个持久化产物由什么配置、输入和版本生成
```

示例：

```text
IndexManifest
```

### 8.2 Manifest 的职责

Manifest 负责记录：

1. 产物 ID。
2. 创建时间。
3. 关键配置。
4. 输入数据版本。
5. 统计信息。
6. config hash。

Manifest 不负责：

1. 保存完整业务数据。
2. 保存 API key。
3. 执行构建流程。
4. 执行检索。

### 8.3 ManifestStore 或 ManifestRepository

当前已有：

```text
IndexManifestStore
```

后续如果统一 Collection/Repository 命名，可以考虑改为：

```text
IndexManifestRepository
```

原因是 manifest 读写也是一种持久化适配器。

但短期内可以保留现名，避免在子模块 4 期间过度重构。

## 9. Registry

### 9.1 命名规则

```text
Registry
  策略、插件或实现类的注册表
```

示例：

```text
ChunkerRegistry
```

### 9.2 Registry 的职责

Registry 负责：

1. 注册策略名和实现类。
2. 校验策略名是否存在。
3. 根据配置创建对应对象。
4. 支持外部扩展策略。

Registry 不负责：

1. 读取 TOML。
2. 运行具体策略。
3. 持久化策略。

---

## 10. Pipeline

### 10.1 命名规则

```text
Pipeline
  在线或离线流程编排
```

示例：

```text
IngestionPipeline
RagPipeline
```

### 10.2 Pipeline 与 Builder 的区别

```text
Pipeline
  更通用的流程编排
  可以用于在线请求或离线处理

Builder
  更强调构建某个持久化产物
```

例如：

```text
IngestionPipeline
  文档摄取流程

IndexBuilder
  用 ingestion + chunking + embedding 构建索引产物

RagPipeline
  在线问答流程
```

## 11. Factory

### 11.1 命名规则

```text
factory.py
  composition root
  项目对象组装入口
```

### 11.2 Factory 的职责

Factory 负责：

1. 把 Settings 转换成 Config。
2. 根据配置选择具体实现。
3. 统一注入依赖。
4. 保证同一进程内对象使用一致配置。

Factory 不负责：

1. 执行业务流程。
2. 保存数据。
3. 做相似度搜索。
4. 写报告内容。

### 11.3 禁止隐式默认依赖

不推荐：

```python
class IndexBuilder:
    def __init__(self, vector_collection=None):
        self.vector_collection = vector_collection or InMemoryVectorCollection()
```

推荐：

```python
class IndexBuilder:
    def __init__(self, vector_collection: VectorCollection) -> None:
        self._vector_collection = vector_collection
```

默认实现由 factory 决定，而不是由底层类自己决定。

## 12. 错误命名和过大命名

### 12.1 避免过大的配置段名

如果配置只服务某个类，不要用过大的名字。

不推荐：

```toml
[indexing]
manifest_filename = "manifest.json"
```

因为它看起来像整个 indexing 子系统的配置。

推荐：

```toml
[index_builder]
manifest_filename = "manifest.json"
```

因为这些字段只服务 `IndexBuilder`。

### 12.2 避免 Helper / Manager 泛化

不推荐随意使用：

```text
Helper
Manager
Handler
Processor
Service
Utils
```

除非能明确说明职责。

优先选择更具体的名字：

```text
ChunkingReportWriter
IndexManifestRepository
VectorCollection
DocumentIdentityBuilder
```

### 12.3 避免裸 dict 在系统中流动

不推荐：

```python
{"chunk_id": "...", "text": "...", "metadata": {...}}
```

推荐：

```python
DocumentChunk(...)
VectorRecord(...)
RetrievedChunk(...)
```

字典可以用于 JSON 序列化边界，但进入业务逻辑后应尽量转换为结构化模型。

当前项目已有一些历史命名，不需要一次性全部重构。

建议后续按练习节奏逐步迁移：

### 13.1 Vector 层

当前：

```text
InMemoryVectorStore
LocalJsonVectorStore
```

建议迁移为：

```text
InMemoryVectorCollection
LocalJsonVectorRepository
```

迁移目标：

```text
VectorCollection
  负责 add/search/count/contains/dimension

VectorRepository
  负责 load/save
```

### 13.2 Document 层

当前：

```text
InMemoryDocumentRepository
```

建议拆分为：

```text
InMemoryDocumentCollection
LocalJsonDocumentRepository
```

### 13.3 Chunk 层

当前 chunk 保存在 `InMemoryDocumentRepository` 内。

建议拆出：

```text
InMemoryChunkCollection
LocalJsonChunkRepository
```

### 13.4 Manifest 层

当前：

```text
IndexManifestStore
```

可暂时保留。

后续如统一命名，可改为：

```text
IndexManifestRepository
```

## 14. 后续新增类命名检查清单

新增类之前，先回答以下问题：

1. 它是外部配置结构吗？
   - 是：命名为 `XxxSettings`。
2. 它是功能类运行时配置吗？
   - 是：命名为 `XxxConfig`。
3. 它是内存中的领域数据集合吗？
   - 是：命名为 `XxxCollection`。
4. 它负责持久化读写吗？
   - 是：命名为 `XxxRepository`。
5. 它调用外部服务或模型吗？
   - 是：命名为 `XxxClient`。
6. 它构建复杂产物吗？
   - 是：命名为 `XxxBuilder`。
7. 它加载已有产物并组合多个持久化对象吗？
   - 是：命名为 `XxxLoader`。
8. 它把结果写到文件吗？
   - 是：命名为 `XxxWriter`。
9. 它记录产物生成配置和版本吗？
   - 是：命名为 `XxxManifest`。
10. 它注册策略名和实现类吗？
    - 是：命名为 `XxxRegistry`。

如果一个类很难归入以上任何一类，说明它的职责可能还不够清晰，需要先拆分或重新命名。
