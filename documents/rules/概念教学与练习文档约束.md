# 概念教学与练习文档约束

本文档记录本项目后续学习过程中，生成“概念教学文档”和“练习说明文档”时必须遵循的约束。它适用于 `paper-rag-assistant` 项目的后续所有子模块学习，也可作为后续模块学习文档的默认风格参考。

## 1. 总体原则

1. 文档必须服务于真实工程学习，而不是只服务于演示代码。
2. 文档应帮助学习者理解“为什么这样设计”“工程中如何落地”“以后如何扩展”，而不是只罗列 API 或概念定义。
3. 练习文档应重点讲解整体结构、工程范式、模块边界、数据流、配置流和扩展点。
4. 不再设计过于细碎的代码题，例如单独修改某个正则表达式、补一个很小的条件判断、完成一个孤立工具函数等。
5. 可以保留整体功能型练习，例如新增一个报告模块、接入一种检索策略、设计一个配置分层、扩展一种文档处理流程等。
6. 测试不作为用户练习内容。测试代码、测试用例和自检案例应由助手直接补充完成。
7. 所有说明性内容、注释、练习题目、提示和文档正文默认使用中文。

## 2. 概念教学文档约束

### 2.1 生成时机

1. 每进入一个新的子模块，应先生成概念教学文档，再进入代码实践。
2. 生成前应先查看对应模块学习路线，确认本子模块的学习目标、实践目标和验收标准。
3. 如果现有代码已经演进，应结合当前工程状态讲解，而不是只按最初路线文档抽象说明。

### 2.2 推荐文件位置与命名

1. 概念教学文档默认放在 `documents` 目录下。
2. 推荐命名格式为：`子模块N_主题_概念教学.md`。
3. 文件名应体现子模块编号和核心主题，避免使用过于泛化的名称。

### 2.3 内容结构

概念教学文档应至少覆盖以下内容：

1. 本子模块的学习定位：它在整个 RAG 系统中的位置。
2. 本子模块要解决的真实工程问题。
3. 核心概念定义：包括是什么、为什么需要、解决什么问题。
4. 核心概念作用：包括在系统运行链路中的职责。
5. 工程实现方式：包括常见类、接口、模块、数据结构和配置方式。
6. 真实场景注意事项：包括性能、稳定性、可维护性、扩展性和常见失败模式。
7. 与当前项目的关联：说明这些概念会映射到哪些代码模块或后续练习。
8. 学习检查清单：用于判断是否可以进入实践阶段。

### 2.4 内容风格

1. 初次接触的新概念必须详细解释，不能只给简短定义。
2. 理论知识和工程落地应同时出现。理论用于理解边界，工程用于理解取舍。
3. 对抽象概念应给出具体例子，例如文档、论文、chunk、embedding、query、retrieval result 等。
4. 应说明常见误区，例如把 demo 流程当成真实工程、把配置读取和业务对象耦合、把存储对象和内存管理对象混为一谈等。
5. 文档应避免空泛表述，例如“提升效果”“更加灵活”等，如果使用这类说法，应进一步解释提升的对象、原因和代价。

## 3. 练习说明文档约束

### 3.1 生成时机

1. 练习说明文档应在对应功能代码生成或重构之后编写。
2. 文档必须解释已经生成的代码，而不是只给任务清单。
3. 如果代码结构发生变化，练习文档也要同步更新，避免文档与代码脱节。

### 3.2 推荐文件位置与命名

1. 练习说明文档默认放在 `documents/exercise` 目录下。
2. 推荐命名格式为：`README_submodule_N.md`。
3. 如果一个子模块拆分成多个阶段，可以在文件名中追加主题，但应保持编号清晰。

### 3.3 必须讲解的内容

练习说明文档应至少覆盖以下内容：

1. 本次练习目标：本子模块最终希望形成什么工程能力。
2. 代码总览：列出新增或重点修改的目录和文件。
3. 整体架构：说明模块边界、依赖方向、核心抽象和组合方式。
4. 数据流动路线：说明数据从输入到输出经过哪些对象、方法和文件。
5. 配置流动路线：说明外部配置如何转成 Settings，再如何适配为功能类使用的 Config。
6. 关键类与接口：解释每个核心类负责什么、不负责什么。
7. 工厂层或组合根：说明对象如何统一组装，避免业务类私自创建依赖。
8. 运行方式：说明如何执行相关命令、需要哪些环境变量或配置项。
9. 自检方式：说明已有测试、自检脚本或人工检查点。
10. 后续扩展方向：说明真实工程中可以继续扩展哪些能力。

### 3.4 练习题设计约束

1. 练习题应聚焦工程结构、模块设计、范式规划和真实功能扩展。
2. 练习题可以要求用户新增一个模块、接入一种策略、调整一层抽象、补充一种报告或扩展一个流程。
3. 练习题不应要求用户专门完成测试代码。测试应由助手直接编写。
4. 练习题不应长期停留在微观实现细节，例如单个正则、单个字段映射、单个异常分支。
5. 练习题应让用户理解全局工作流程，同时接触关键工程决策。
6. 如果某个具体算法或细节对主线学习价值较低，可以由助手直接实现，并在文档中讲解。

### 3.5 TODO 与占位代码约束

1. 可以保留少量 TODO，但 TODO 应围绕扩展点、工程边界或完整功能模块。
2. 不应为了制造练习而留下影响主流程可运行性的核心缺口。
3. 不应留下大量占位实现、mock-only 实现或明显不符合真实工程的简化逻辑。
4. 如果暂时使用 mock、baseline 或简化实现，必须在文档中说明原因、边界和后续替换方案。

## 4. 代码讲解约束

1. 练习文档必须仔细讲解生成代码，不能只说“代码已完成”。
2. 对重要代码应解释它为什么这样拆分，而不是只解释每行做了什么。
3. 应说明类之间的依赖方向，尤其是 Settings、Config、Factory、Repository、Collection、Service、API Handler 之间的关系。
4. 应说明哪些对象属于外部配置读取，哪些对象属于运行期业务配置，哪些对象负责文件或数据库交互，哪些对象负责内存态数据组织。
5. 如果引入注册表、策略模式、协议接口、工厂模式、依赖注入等工程模式，必须解释其使用场景和代价。

## 5. 真实工程约束

1. 后续功能代码应尽量贴近真实工程，而不是只做 demo。
2. 文档加载、解析、清洗、切分、索引、检索和生成等环节，应优先使用真实论文、Markdown、HTML 或其他真实文档场景。
3. 对环境配置、依赖安装、外部服务接入等内容，只写入说明文档，不直接修改用户环境。
4. 如果需要新增第三方库，应说明库名、用途、安装方式和为什么选择它。
5. 如果存在成熟工程库或行业常用方案，应主动介绍，并说明本项目当前选择自建实现或轻量实现的原因。

## 6. 与既有项目规则的关系

1. 命名分层仍遵循 `documents/rules/工程命名与分层约束.md`。
2. 工具与版本管理仍遵循 `documents/rules/工具使用与版本管理约束.md`。
3. 外部配置读取类统一命名为 `Settings`。
4. 转换后供功能类实际使用的运行期配置类统一命名为 `Config`。
5. 与文件、数据库等持久化介质交互的类使用 `Repository` 命名。
6. 管理已加载或已处理内存态数据集合的类使用 `Collection` 命名。
7. 不使用 `Store` 作为新的核心分层命名，除非引用第三方库既有概念且无法避免。

## 7. 验收标准

生成概念教学文档或练习说明文档后，应检查以下事项：

1. 是否覆盖了学习路线中对应子模块的全部核心内容。
2. 是否解释了概念的定义、作用、工程位置和常见问题。
3. 是否结合了当前项目代码，而不是脱离工程单独讲理论。
4. 是否避免了过度 demo 化、占位化和细碎任务化。
5. 是否清楚说明了运行方式、配置方式和自检方式。
6. 是否保留了足够的工程练习空间，但没有把测试工作转嫁给用户。
7. 是否与现有命名、配置、Repository、Collection、Factory 等项目约束一致。
