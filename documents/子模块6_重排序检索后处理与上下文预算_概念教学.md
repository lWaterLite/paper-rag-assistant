# 子模块 6：重排序、检索后处理与上下文预算

## 1. 学习定位

本子模块位于“检索”与“回答生成”之间。它不解决“如何从知识库找到候选资料”，而是解决一个更贴近真实 RAG 系统的问题：当系统已经找到一批看起来相关的 chunk 后，哪些 chunk 值得进入模型上下文，它们应该以什么顺序、什么长度和什么来源关系被组织起来？

当前项目已经具备以下基础：

```text
query
  -> VectorRetriever / BM25Retriever / HybridRetriever
  -> RetrievalPipeline
  -> 去重与 TopKLimitStage
  -> SimpleContextPacker（字符预算、去重、相邻合并、citation）
  -> RagPipeline
```

其中 `HybridRetriever` 已通过加权 RRF 将 vector 与 BM25 的排名融合，`SimpleContextPacker` 已经能去重、合并相邻 chunk 并生成 citation。它们是本子模块的起点，而不是需要重新实现的内容。

本子模块要把这条链路深化为：

```text
query
  -> 候选召回（vector / BM25 / hybrid）
  -> 候选去重
  -> rerank
  -> 最终 top-k
  -> token-aware context packing
  -> 可追溯上下文段
  -> 子模块 7 的 AnswerGenerator
```

这里有一个重要边界：子模块 6 只确保“交给生成器的证据足够好且可追溯”。如何改写 query、如何让 LLM 生成答案、如何校验回答中的引用，仍属于子模块 7；如何用大规模题集和指标证明优化有效，仍属于子模块 8。

## 2. 本子模块要解决的真实工程问题

### 2.1 召回正确，不等于上下文正确

假设用户提问：

```text
RAG 中 rerank 的作用是什么？它有什么代价？
```

hybrid retrieval 可能返回如下候选：

```text
1. "Rerank 能改善最终排序"                只覆盖作用
2. "Cross-encoder 的推理成本更高"          只覆盖代价
3. "BM25 的公式与参数"                     关键词相近但答非所问
4. "Rerank 在候选集上重排并增加延迟"        同时覆盖作用与代价
5. "某论文的实验设置"                      辅助信息
```

“召回”希望候选集合尽量不要漏掉第 4 条；“重排序”希望第 4 条排到最前；“上下文组织”希望在有限预算中保留第 4 条，并补充必要证据，而不是把第 1、2、3 条的重复内容塞满上下文。

因此，这里至少有三个不同目标：

| 阶段 | 主要目标 | 典型失败 |
| --- | --- | --- |
| 召回 | 覆盖可能相关的证据 | 关键 chunk 根本没有被找到 |
| Rerank | 让最能回答当前问题的候选排前面 | 泛相关内容排名高于直接证据 |
| Context packing | 在窗口内保留多样、可引用的证据 | 重复、超长或不可追溯内容挤掉关键信息 |

把三者混成一个“大检索函数”，会让后续很难知道问题究竟来自 embedding、BM25、融合、重排序还是上下文预算。

### 2.2 模型上下文窗口是真实资源约束

模型并不按字符数接收文本，而是按 token 接收。中文、英文、公式、URL、论文引用和 Markdown 标记的 token 比例差异很大，所以当前 `max_context_chars` 只能作为早期近似，不能成为真实模型接入后的边界。

一个请求可放入的资料预算更接近：

```text
可用资料 token
  = 模型上下文窗口
  - system prompt token
  - 用户问题 token
  - citation 与格式开销
  - 预留输出 token
  - 安全余量
```

如果没有预留输出空间，模型可能在回答还未生成完时达到窗口上限；如果只计算 chunk 正文，则 citation 前缀和提示词本身也可能使请求超限。

## 3. 两阶段检索

### 3.1 什么是 two-stage retrieval

两阶段检索把“找得全”和“排得准”拆开：

```text
第一阶段：candidate retrieval
  快速从大量 chunk 中召回较宽的候选集合，例如 20 条。

第二阶段：reranking
  对候选集合逐个或成组细看 query 与 chunk 的关系，再挑出最终 3 到 5 条。
```

第一阶段通常使用 bi-encoder 向量检索、BM25 或 hybrid，因为它们可以高效搜索大量数据。第二阶段通常使用更慢但更精细的模型，因为它只处理少量候选。

### 3.2 `candidate_limit` 与最终 `top_k`

这两个数字必须分开表达：

```text
candidate_limit
  rerank 之前最多交给后处理流程多少条候选。

top_k
  rerank 与最终选择完成后，对下游 ContextPacker 暴露多少条结果。
```

例如：

```text
candidate_limit = 20
top_k = 5
```

这并不表示最终回答会使用 20 个 chunk。它表示先让 reranker 看 20 条，最后只把其中前 5 条交给 context packing。若没有 rerank，候选上限与最终 top-k 可以相同，从而保留当前项目的行为。

当前 `RetrievalPipeline` 把 `top_k` 同时用于 retriever 输入与最终 `TopKLimitStage`。这对 baseline 足够，但不足以表达两阶段检索；子模块 6 将把候选数量和最终数量拆开，同时保持 `Retriever` 协议只负责“给出候选”的职责。

### 3.3 Rerank 不能弥补召回遗漏

Reranker 只能对传入的候选重新排序。若 vector、BM25 和 hybrid 都没有召回某条关键信息，reranker 没有机会看到它，也无法凭空生成它。

所以优化顺序通常是：先确认候选集合包含答案证据，再讨论 rerank 是否能把证据排到前面。把“没有召回到”误判为“rerank 不够强”，是常见的诊断错误。

## 4. Reranker

### 4.1 定义与作用

Reranker 是接收 `(query, candidates)` 并返回重新排序候选的组件。它不负责读取索引、生成 embedding、加载 JSON 或直接构建回答。

它的作用是回答一个比向量相似度更精细的问题：

```text
这个具体 chunk 是否能直接支持当前这个具体 query？
```

向量检索通常分别把 query 和 chunk 编成向量，再用相似度比较；reranker 可以同时看到 query 和 chunk 的完整文本，从而识别限定词、否定关系、比较关系和局部事实。

### 4.2 Bi-encoder 与 cross-encoder

| 模型类型 | 编码方式 | 主要优势 | 主要代价 | 工程位置 |
| :--- | :--- | :--- | :--- | :--- |
| Bi-encoder（双塔模型） | query 与 chunk 分别编码，再比较向量 | 可预先建立索引，搜索快 | 对细粒度匹配较弱 | 大规模候选召回 |
| Cross-encoder（交叉编码器） | 将 query 与 chunk 一起输入模型 | 相关性判断更细 | 每个候选都要推理，延迟更高 | 小候选集合的 rerank |

Cross-encoder 常见输入形态是：

```text
[CLS] query [SEP] chunk text [SEP]
```

它可以关注 query 中的“代价”“区别”“是否”等词与 chunk 中相应句子的关系。代价是候选数量每增加一倍，推理成本也大致随之增加，因此它不适合直接扫描全量知识库。

### 4.3 Pointwise、pairwise 与 listwise

这三类术语描述模型学习或执行排序时关注的对象：

```text
pointwise
  独立给每个 (query, chunk) 打相关性分数。

pairwise
  判断两个候选中哪个对 query 更相关。

listwise
  直接考虑整个候选列表的排序质量。
```

工程上最常见、最易接入的是 pointwise reranker：批量给每个候选打分后排序。它的接口清晰、可批处理，也容易用确定性本地实现测试。pairwise 与 listwise 可能带来更好的排序建模，但接口、成本、稳定性和调试难度都更高。

### 4.4 Rerank score 不是通用分数

以下数值不能直接相加或跨系统比较：

```text
cosine similarity
BM25 score
RRF score
cross-encoder score
LLM judge score
```

它们的范围、分布和含义不同。对下游流程，稳定的排序 `rank` 往往比原始 score 更可靠。原始分数应保留在本次运行的结构化诊断信息中，用于排查，不应覆盖文档 metadata，也不应被误当作概率。

### 4.5 推荐接口边界

本项目后续适合采用类似以下的结构：

```python
class Reranker(Protocol):
    def rerank(
        self,
        query: str,
        candidates: Sequence[RetrievedChunk],
        *,
        limit: int,
    ) -> list[RerankedCandidate]:
        ...
```

`RerankedCandidate` 应保留原 `RetrievedChunk`，并额外描述：

```text
rerank_score
rerank_rank
reranker_strategy
原始 retrieval signals
```

不要直接修改 `DocumentChunk.metadata`。文档 metadata 是离线、稳定的文档事实；rerank score 是一次 query 执行时才出现的运行时证据。

### 4.6 本地 baseline 与真实模型 adapter

为了让测试和学习不依赖下载模型，本子模块应先提供确定性的本地 baseline，例如基于 query token 覆盖度、短语命中或字段加权的 `LexicalReranker`。它不是为了模拟 cross-encoder 的质量，而是为了验证：

```text
配置 -> registry -> RerankStage -> trace/report -> 最终排序
```

真实 cross-encoder 或远程 rerank 服务应被封装为独立 adapter/client。它只接收已经转换好的 `RerankConfig` 和候选，不读取整个 `ProjectSettings`，不自行创建模型，也不直接写日志。Factory 决定何时注入该实现。

## 5. Rerank 作为检索后处理阶段

### 5.1 为什么不能放进 `HybridRetriever`

`HybridRetriever` 的职责是组合多个召回源并进行 RRF 融合。若它内部再执行 rerank，会带来三个问题：

1. vector-only 与 BM25-only 无法复用 rerank。
2. `hybrid` 不再是普通 `Retriever`，策略职责开始膨胀。
3. compare search 不能区分“融合造成的排序”与“rerank 造成的排序”。

正确的依赖方向是：

```text
Retriever
  负责候选召回。

RetrievalResultStage
  负责对候选做通用后处理。

RerankStage
  是其中一个可配置阶段。
```

建议的执行顺序是：

```text
retrieve(candidate_limit)
  -> ChunkIdDeduplicationStage
  -> RerankStage（可关闭）
  -> FinalTopKStage
  -> ContextPacker
```

去重应在 rerank 前完成，避免对完全重复的 chunk 重复付费；最终 top-k 应在 rerank 后执行，否则 reranker 看不到足够宽的候选集合。

### 5.2 fail-open 与 fail-closed

真实 reranker 可能因模型加载、网络、超时或限流失败。此时必须提前定义策略：

```text
fail-open
  记录 rerank 失败并沿用原排序继续请求。
  适合强调可用性的交互式问答。

fail-closed
  让请求失败并返回明确错误。
  适合 rerank 是质量或合规硬约束的场景。
```

无论选择哪种策略，都不能静默吞掉异常。trace 与 retrieval report 至少应记录 reranker 名称、候选数量、耗时、错误信息、是否降级和最终使用的排序来源。

### 5.3 Registry、Settings、Config 与 Factory

本项目已经为 chunker、tokenizer、retriever 建立了 registry 范式。Reranker 应沿用同一条配置流：

```text
settings.toml [retrieval.reranking]
  -> RerankingSettings
  -> ConfigFactory.build_reranking_config()
  -> RerankingConfig
  -> RerankerRegistry.resolve(strategy)
  -> RerankStage
```

其中：

```text
RerankingSettings
  外部 TOML 的结构与校验。

RerankingConfig
  运行时实际参数，例如 enabled、strategy、candidate_limit、batch_size、failure_mode。

RerankerRegistry
  策略名到 provider 的映射与合法性校验。

RerankStage
  在 pipeline 中调用已注入的 Reranker，不自行构造默认依赖。
```

这保证未来加入 `cross_encoder`、远程 API 或专用检索服务时，不需要把 `if strategy == ...` 散落到 pipeline、API 或业务对象中。

## 6. Token-aware Context Packing

### 6.1 Tokenizer 不等于 TokenEstimator

当前 `RegexTokenizer` 服务于 BM25：它决定怎样把文本分词并统计词频。它不能保证与生成模型的 token 计数一致。

`TokenEstimator` 的职责不同：它估算某个模型实际会消耗多少上下文 token。即使早期使用近似实现，也必须单独命名和注入，避免把“检索分词规则”误用为“模型窗口预算规则”。

可替换实现可以包括：

```text
RegexTokenEstimator
  不依赖外部库，适合测试和无模型环境，但只是近似。

TiktokenTokenEstimator
  适合兼容 OpenAI tokenizer 的模型。

ProviderTokenizerEstimator
  调用或复用具体模型提供方的 tokenizer。
```

新增第三方 tokenizer 时，应只在说明文档中列出依赖和安装方式，由用户自行配置环境。

### 6.2 预算模型

更可靠的配置不是单一 `max_context_chars`，而是可解释的 token 预算组成：

```text
model_context_window
reserved_output_tokens
prompt_overhead_tokens
safety_margin_tokens
max_context_tokens
max_chunks_per_document
```

其中可放入资料的预算可由固定 `max_context_tokens` 控制，也可以由窗口推导。工程上应明确选择一种来源，避免两个相互矛盾的上限同时生效而无人知道谁优先。

在本项目中，建议把请求级问题、citation 前缀、段落分隔符都作为实际文本送入 estimator，再根据真实 token 使用量决定是否放入下一个候选。

### 6.3 Context packing 是选择，不是摘要

ContextPacker 的核心职责是：

```text
输入：已排序的 RetrievedChunk[]
输出：满足预算、去重、可解释、可追溯的 PackedContext
```

它应完成：

1. 按 chunk id 与规范化文本去重。
2. 控制单篇文档最多占用的证据数量，避免一篇论文垄断上下文。
3. 在明确满足位置连续条件时合并相邻 chunk。
4. 为每个未采用候选记录原因，例如重复、超过预算、文档配额或低排序。
5. 为每个上下文段记录完整 `source_chunk_ids`、页码范围和章节范围。

当前 `SimpleContextPacker` 已完成前两类基础行为与相邻合并，但它使用字符预算，且合并后的一个 `Citation` 只保存第一个 chunk id。`used_chunks` 仍保留完整列表，所以数据并未消失；不过对于后续严格 citation 校验，仍需增加“上下文段到全部来源 chunk”的结构化映射。

### 6.4 合并、截断与证据归属

相邻 chunk 合并能避免句子被切断，但也会产生一个来源表示问题：

```text
chunk_12 + chunk_13
  -> 一个 context segment
```

若只把 `chunk_12` 作为 citation，读者无法知道 segment 后半部分来自 `chunk_13`。更稳妥的中间结构是：

```text
ContextSegment
  text
  source_chunk_ids
  source_doc_id
  page_start / page_end
  section(s)
  token_count
```

子模块 6 负责保留这个 provenance；子模块 7 再决定回答文字中的 citation id 如何引用和校验这些来源。

### 6.5 Context compression 的边界

压缩有两类：

```text
extractive compression
  从原文选择句子、段落或窗口，不改写事实。

generative compression
  使用模型改写或摘要原文。
```

extractive compression 可以在本子模块作为可追溯的 packing 扩展：输出文本必须能够定位回原始 chunk 范围。Generative compression 虽然节省窗口，但可能遗漏限定条件、混合多个来源或产生没有出处的新表述。由于本项目的回答生成与 citation 校验将在子模块 7 才完善，generative compression 此时只学习概念和接口边界，不接入主流程。

## 7. 与当前项目的代码映射

| 当前组件 | 当前职责 | 子模块 6 的演进方向 |
| --- | --- | --- |
| `Retriever` | 根据 query 召回 `RetrievedChunk` | 继续只负责候选召回 |
| `HybridRetriever` | vector 与 BM25 的 RRF 融合 | 作为 rerank 前的一个候选来源，不内嵌 rerank |
| `RetrievalPipeline` | 解析策略、执行检索、去重、最终截断、写报告 | 显式区分 candidate 与 final 阶段，接入 `RerankStage` |
| `RetrievalResultStage` | 通用结果后处理 | 新增可配置的重排序阶段 |
| `SimpleContextPacker` | 字符预算下去重、合并与 citation | 升级为 token-aware、带 ContextSegment provenance 的 packer |
| `RetrievalReporter` | 保存单策略检索报告 | 补充 rerank 与 token packing 的阶段事实 |
| `CompareSearchService` | 并列观察多个检索策略 | 保持观察职责，不把它变成融合或评测框架 |
| `ApplicationFactory` / `RetrievalFactory` | 统一组装配置与依赖 | 新增 reranker、token estimator 的显式装配 |

建议的软件包边界如下：

```text
app/retrieval/
  rerankers/
    base.py
    registry.py
    lexical.py
    config.py
    stage.py

  token_estimators/
    base.py
    registry.py
    regex.py
    config.py

  context_packer.py
    ContextSegment
    PackedContext
    TokenAwareContextPacker
```

这是后续练习可采用的方向，不表示现在要一次性引入所有真实模型 adapter。Factory 仍是唯一组装点：业务类只接收 `Config` 和抽象依赖，不读取 TOML，不调用默认构造器偷偷创建实现。

## 8. 性能、稳定性与可维护性

### 8.1 延迟与批处理

若 cross-encoder 要对 20 个候选逐个推理，延迟可能远高于向量搜索。常见控制手段是：

```text
控制 candidate_limit
批量 rerank
设置 timeout
设置最大文本长度
缓存重复 query 的短生命周期结果
失败时按策略降级
```

这些措施不能改变语义边界：缓存属于后续生产化优化，timeout 与错误转换属于 client adapter，是否继续请求属于 pipeline 的 failure mode。

### 8.2 配置漂移

检索报告必须记录本次实际使用的 reranker strategy、候选上限、token estimator 和预算参数。否则以后看到“这次回答为什么变了”时，无法区分是索引、检索策略、rerank 配置还是 packing 预算改变。

延续项目约束：外部 TOML 对应 `Settings`，功能类接收 `Config`，二者由 `ConfigFactory` 转换。不要把 `ProjectSettings` 传入 `RerankStage`、`ContextPacker` 或模型 client。

### 8.3 常见失败模式

| 现象 | 更可能的原因 | 首先检查 |
| --- | --- | --- |
| Rerank 后答案更差 | 候选过少、reranker 与领域不匹配、截断了关键证据 | candidate_limit、候选文本长度、rerank 前后 rank |
| Rerank 没有变化 | 配置未启用、stage 顺序错误、候选只有最终 top-k 条 | registry、trace、candidate_count |
| 上下文超窗 | 用字符数估算、未计算 prompt/输出、citation 开销遗漏 | token estimator、预算明细 |
| 证据重复 | 去重只按 chunk id、不同 chunk 文本高度重叠 | content dedup、文档配额、合并规则 |
| 引用范围不准确 | 合并段只指向第一个 chunk | ContextSegment provenance |
| 服务偶发变慢 | cross-encoder 每请求重复加载或候选过宽 | Factory 生命周期、batch、candidate_limit |

## 9. 本子模块不做什么

为保护后续学习顺序，本子模块明确不做以下工作：

1. 不实现 query rewrite、multi-query、HyDE、真实回答生成和回答文本 citation 校验；这些属于子模块 7。
2. 不创建 golden dataset、Recall@k、MRR、Ragas、实验运行器或配置实验矩阵；这些属于子模块 8。
3. 不接入 FastAPI、SSE、应用生命周期、通用结构化日志或线上 API；这些属于子模块 9。
4. 不实现权限过滤、prompt injection 防护、限流、Docker、CI 或生产成本治理；这些属于子模块 10。
5. 不重新实现 vector、BM25、RRF hybrid 或 compare search；它们是本子模块需要保持稳定的前置能力。

## 10. 学习检查清单

进入实践前，你应能回答：

1. 为什么 reranker 不能替代 retriever？
2. 为什么 `candidate_limit` 必须大于最终 `top_k` 才有 rerank 的意义？
3. 为什么 cross-encoder 更适合作为第二阶段，而不是全库检索器？
4. 为什么 BM25 tokenizer 不能直接代表生成模型的 token 预算？
5. 为什么 rerank score 不应覆盖原始 retrieval score 或写入 document metadata？
6. 为什么 context packing 必须保留 dropped reason 与完整来源 chunk 列表？
7. fail-open 与 fail-closed 分别适合什么业务约束？
8. 为什么此时不应该建立完整评测集和实验 runner？

如果这些问题已经清楚，就可以开始子模块 6 的工程实践：先建立 reranker 与 token estimator 的边界，再将它们接入现有 retrieval pipeline，而不是从头重写已经稳定的 hybrid 与 context packing。
